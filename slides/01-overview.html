目標と確かめ方を渡せば、
エージェントが開発を進める。

A1〜A8 と D02 を全部取り入れると、目標と確かめ方を渡すだけで、エージェントが計画・実装・検証まで進める。人は承認ボタンではなく、レビューと判断に時間を使える。

4つの柱: 目標を渡す／自分で確かめさせる／仕組みで守る／並べて任せる。

関連する章A3 /goalD02 つまずきやすい点

任せられる

条件を満たすまで、エージェントは終われない。

  • 先に Shift+Tab で auto mode にする。/goal は権限モードを変えないので、Manual のままだと npm test のたびに確認が出る。
  • /goal を設定した時点で、その条件を指示として1ターン目が始まる。ターンごとに小さなモデルが条件を判定し、満たすまで続けさせる。
  • Stop hook は終わろうとするたびにスクリプトが走り、終了コード 2 で差し戻す。stop_hook_active を見て差し戻しを一度に限り、回り続けを防ぐ。

自分で確かめる

いちばん効くのは、確かめる手段を渡すこと。

確かめる手段を渡すのが最も大事で、最終結果が2〜3倍よくなる（Boris Cherny の見積もり。2026-10-15 の記事が引用）。数字は見積もりであり、計測値ではない。

テストの実行方法を CLAUDE.md に書いておく（A4）。

関連する章A3 確かめ方を渡すA4 CLAUDE.md

自分で確かめる

注意に頼らず、仕組みで確かめさせる。

  • 強さ1 プロンプトに書く: 手軽。忘れられることがある。
  • 強さ2 /goal: 小さなモデルが条件を判定し、満たすまで続けさせる。
  • 強さ3 Stop hook: 終わろうとするたびにスクリプトが走る。終了コード 2 で差し戻す。決定的。
  • 強さ4 検証 subagent・/code-review: 別の context で、書いた本人以外が確かめる。レビューの往復は3回で打ち切る。
関連する章A3 確かめ方を渡すA5 subagentsA7 Writer / Reviewer

安全に任せる

auto mode は、危険な操作だけを止める。

  • auto mode では分類モデルが操作を審査し、危険なものだけ止める。v2.1.283 から起動時の既定。
  • 3回続けて、または合計20回止めると一時停止し、確認ありに戻る。
  • 他のモード: default（読み取りだけ）／acceptEdits／plan／dontAsk（headless 向け）／bypassPermissions（隔離環境以外では使わない）。
関連する章A6 auto mode

安全に任せる

止めたい操作は、仕組みで必ず止める。

  • CLAUDE.md: Claude の注意に頼る。破っても大きな害がないことに使う。
  • deny ルール: どのモードでも効く。allow より優先。例 "deny": ["Bash(git push *)"]
  • PreToolUse hook: スクリプトが直前に走り、終了コード 2 で理由付きで止める。
  • sandbox: 書き込める場所と通信先を OS レベルで制限し、被害の範囲を絞る。
  • 既定が auto でも、deny ルール・hooks・sandbox を重ねる考え方は変わらない。
関連する章A6 hooks・permissions・sandbox

並べて任せる

1つを信頼できてから、並べて任せる。

前提: 1つのセッションを信頼できてから並べる。確かめ方（A3）と守り（A6）が無いと、確かめていない変更が並列に増える。

関連する章A3 確かめ方A6 守るA7 並列

並べて任せる

手元で並べ、クラウドに渡し、時刻で動かす。

  • worktree（claude -w add-search）: 作業ごとに checkout とブランチを分ける。書いたセッションとは別のセッションにレビューさせる。並列のタスクはファイルの境目で分ける。
  • cloud sessions: タスクごとに新しい VM。手元で計画し、クラウドで実装し、teleport で戻す。依頼は確かめ方まで書いた自己完結したチケットに。
  • scheduled tasks: スケジュール（最短で毎時）・HTTP エンドポイント・GitHub のイベントで起動し、毎回 cloud session として動く。承認の確認なしで動き、既定では claude/ で始まるブランチに push する。手元なら Desktop や /loop。
関連する章A7 並列に動かすA8 クラウドで動かす

Grok Bot ＋ pstack

Grok Bot と pstack でも、同じ考え方を回す。

  • 完了条件を渡す → /poteto-mode ＋ 目標 ＋ 合否を判定できる完了条件
  • 自分で確かめさせる → /create-verification-skill で、エージェントがアプリを自分で動かして確かめる
  • 決まった時刻に動かす → ルーティン（「毎朝9時に〜を確認して」）
  • 並べる → /swarm・/arena。同じファイルは worktree かクラウドに分離
  • 間違いを仕組みにする → 同じ指示を2回書いたらスキルにする。/reflect・/correct
  • 対応づけは、この教材での見立て。pstack の README の標語は「go fast するなら、まず go deep」。外部への送信・投稿・購入は毎回ユーザーの承認が要る。
関連する章D02 Grok Bot の環境を整える

人の役割

人の時間は、承認からレビューと判断へ。

エージェントが計画・実装・検証まで進めるので、人は承認ボタンではなく、レビューと判断に時間を使える。人の承認の数は、変更のリスクで決める（A7）。

関連する章A7 並列に動かす

1日の流れの例

朝に渡し、昼に見て、夜は直させる。

これは各章の仕組みを組み合わせた一例で、決まった手順ではない。

  • 朝: plan mode で計画を立ててコミット（A2）。背景・やること・確かめ方を書いたチケットを cloud session や worktree に配る（A7・A8）。各セッションに /goal で完了条件を渡す（A3）。
  • 昼: 書いたセッションとは別の context や /code-review にレビューさせる（A3・A7）。人の承認の数は変更のリスクで決める（A7）。teleport で手元に移し npm test で確かめる（A8）。
  • 夜: Auto-fix・/autofix-pr で失敗したチェックやレビューコメントに対応させる（A8）。あいまいな点や設計に関わる点は Claude が人に聞く（A8）。scheduled tasks や Grok Bot のルーティンで翌朝の点検を回す（A8・D02）。

まとめ

まずは、確かめ方を渡すことから。

  1. 確かめ方を渡す: テストの実行方法を CLAUDE.md に書き、Stop hook と /goal で「通るまで終われない」にする（A3・A4）。
  2. 守りを仕組みにする: auto mode で確認の手間を減らし、deny ルール・PreToolUse hook・sandbox を重ねる（A6）。
  3. 任せる範囲を広げる: 1つのセッションを信頼できてから、worktree・cloud sessions・scheduled tasks・Grok Bot のルーティンへ広げる（A7・A8・D02）。

まずは「この教材の使い方」で workspace を作り、A1 から順に進める。
